# ReviewCrew 评测报告

## 报告状态

本报告记录当前仓库中可复现的工程验证，以及正式 Greptile 50-PR 评测尚缺少的外部输入。当前 `benchmark/dataset.yaml` 为空，因此不能诚实计算正式命中率、平均误报或平均耗时。`benchmark/public_sample.yaml` 是一个经过 GitHub 元数据核验的公开单案例，仅用于冒烟验证，不构成正式成绩。

内置 Replay 和 Benchmark 演示行只用于验证 UI、事件契约和可视化，不属于 Greptile 评测结果。

## 目标

| 指标 | 目标 | 当前正式结果 | 状态 |
|---|---:|---:|---|
| 目标漏洞命中率 | ≥ 60% | 未评测 | 等待授权数据集 |
| 平均 Finding 数 | ≤ 8 | 未评测 | 输出层已强制 Top 8 |
| 平均耗时 | ≤ 8 min | 未评测 | 任务与全局预算已实现 |
| 硬超时 | ≤ 10 min | 未评测 | 服务配置默认 600 秒 |

## 数据集要求

正式数据集应包含 5 个仓库、每仓库 10 个真实漏洞 PR，并覆盖 Python、Go、TypeScript、Rust 和 Java。每条记录必须具备：

- 上游仓库与组织有权访问的 fork URL。
- PR URL、base SHA 和 head SHA。
- 预期 bug 描述。
- 一个或多个漏洞文件及行区间。
- security、logic、memory、architecture 或 static 分类。

仓库只提供 schema 和导入入口，不会根据公开页面猜测或构造这些字段。

## 判定方法

每个 case 采用两级判定：

1. Finding 文件一致，且行区间与目标区间在 ±10 行容差内重叠，记为 `line_overlap`。
2. 行号未命中时，由独立结构化模型 judge 比较 Finding 的根因、触发路径与目标 bug，只有具体失败模式一致才记为 `semantic_match`。
3. 两级均不满足，记为 `miss`。

输出包含逐 PR 的命中状态、判定原因、Finding 数和耗时，并汇总仓库 × 缺陷类型矩阵。

## 防止指标污染

- `--runner fake` 只测试 harness 的文件生成和报告路径，不应进入正式报告。
- `/benchmark` 在没有结果时显示“演示数据”标记。
- 正式结果必须来自 `--runner real`，且 `dataset.yaml` 非空。
- 每个结果目录保留原始 `results.jsonl`，摘要可从原始行重新生成。
- 正式报告应抽检所有 `semantic_match`，防止模型 judge 过宽。

## 工程验证

本地质量门禁覆盖以下行为：

- unified diff 解析及增删改重命名。
- tree-sitter 符号定义、引用、caller/callee 和增量更新。
- Profile 构建、架构摘要和历史修复模式。
- Semgrep、Ruff、OSV provider 的解析与缺失降级。
- ContextPack 聚类和 token 裁剪。
- Agent 工具路径约束、预算和结构化输出。
- Finding 去重、Verifier 判定、0.6 门限、排序和 Top 8。
- Coordinator 动态规划、依赖调度、并发、handoff、Verifier 扇出、Markdown 报告与 GitHub comment 载荷。
- FastAPI、SSE 编码、Replay、运行列表与详情。
- Vue event reducer、demo fixture、三页生产构建。

最终门禁的精确通过数量和构建结果应以交付时运行输出为准，不在此预填动态数字。

## 公开单案例结果

2026-07-29 使用真实 runner 运行了 `benchmark/public_sample.yaml` 中的
[Netflix/metaflow#3069](https://github.com/Netflix/metaflow/pull/3069)。目标问题是
`devcontainer_decorator.py:74-84` 将用户整个 HOME 目录以读写模式挂载进容器，导致
SSH、云服务和浏览器凭据暴露给低信任环境。

| 指标 | 结果 |
|---|---:|
| 命中 | 否 (`miss`) |
| 保留 Finding | 1 |
| 耗时 | 168.54 秒（2.81 分钟） |
| 目标命中率 | 0/1 |

保留结果位于 `_docker_launcher.py:68-73`，内容是 Docker 日志流异常后可能遗留孤儿容器，
并非目标 HOME 挂载漏洞。运行过程中 Coordinator 派发 4 个首轮并发任务，根据高风险候选
动态追加 1 个交叉检查，并为 7 个候选分别创建 Verifier；这证明了动态调度与验证链路，
但不证明检测效果达标。

本次 miss 的直接归因是 `prompt_blind`：Agent 获得了目标文件上下文，却没有把宽范围可写
宿主机挂载形成候选 Finding。针对该问题已进行通用修正：Coordinator 现在读取受限长度的
patch 摘要，可按实际信任边界变化创建任务；Defect 与 Intent 视角新增容器、sandbox、宿主机
秘密和读写挂载范围检查；Agent 达到调用预算时会恢复最近一次 snapshot，而不是丢弃整条任务
分支。修正后的第二次真实模型复测尚未执行，因此本报告不声称目标已经命中。

## Miss 归因

```bash
/Users/xuansama/miniforge3/envs/common/bin/python -m reviewcrew.tools.analyze_miss \
  --run-id <run_id> \
  --expected-bug '<expected root cause and location>'
```

工具给出四类初筛：

| Attribution | 含义 | 后续动作 |
|---|---|---|
| `context_missing` | 没有形成证据调用 | 检查 ContextPack 和工具预算 |
| `prompt_blind` | 已查证但没形成候选 | 补充对应 Agent checklist |
| `verifier_reject` | 候选被 Verifier 淘汰 | 人工复核反证和门限 |
| `judge_error` | 已有保留 Finding 但未判中 | 修正位置或语义判定 |

每轮只改变一个变量，先跑 quick，再决定是否保留并跑 full。记录模板见 `benchmark/results/ITERATION_LOG.md`。
