# ReviewCrew 1.1.6.1 前端作战室与评测矩阵设计

## 1. 背景与目标

当前前端已经能发起审查、订阅 SSE、展示阶段状态、候选问题、最终报告和历史回放，但“过程展示”仍停留在状态摘要层面：多个专家实例被折叠、工具数量经常为零、时间线只显示最近事件、切换页面后实时订阅随页面销毁，五仓评测区也只有写死的“暂无逐仓数据”。这使系统最有竞争力的并行 Agent Team、Mailbox 协作和独立验证机制没有被清楚表达。

`feature-1.1.6.1-mw` 的目标是把前端升级为可持续观察的“实时 Agent 作战室”，同时补齐页面生命周期和五仓评测展示。所有展示必须来自公开、可追溯的数据，不伪造工具调用，不用 Fake 成绩冒充真实 Benchmark。

## 2. 已确认的产品决策

1. 采用组合方案 C：上半屏展示并行 Agent 拓扑，下半屏展示证据、候选和裁决流水线。
2. 采用全局交互 A：顶部常驻迷你任务条，切换页面后仍可查看当前任务并一键返回作战室。
3. 五仓未运行或未补齐的数据统一显示“待评测”或“待补齐”，不放置推测成绩。
4. 工具展示覆盖整个审查系统，但必须区分“系统工具”和“Agent 工具”。加载 PR、解析 Diff、读取文件、检索符号、读取测试、Git blame、Semgrep 等都可以计入工具活动；模型内部没有实际调用的工具不得伪造成调用。
5. 不展示隐藏思维链、原始 Prompt、模型原始响应、密钥或未经脱敏的外部异常。

## 3. 当前问题与根因

### 3.1 过程展示过于抽象

- 前端只保存 `defect`、`intent`、`verifier` 三个角色状态，真实的 `defect:ctx-1` 等实例被折叠。
- TeamLead 的分片计划已经写入 Mailbox，但没有进入公开 SSE，前端无法展示每个专家负责的文件和风险。
- 时间线只展示最近 10 条事件，无法理解完整的审查因果链。
- 候选、补证、Verifier 接受或拒绝之间缺少可视化关联。

### 3.2 工具数量为零

`run-20260730-012450-d90a1b5b` 包含 37 条公开事件、6 个专家实例和 7 个候选，但没有 `agent.tool` 事件。当前 Context Builder 在 Agent 启动前完成 PR 加载和上下文构建，这些真实操作没有作为公开工具活动展示；专家直接消费预构建上下文时，也不应伪装成主动工具调用。

这里的“工具”不是只指模型临时调用的函数。凡是系统为了完成审查而实际执行的可观察动作，都应显示在过程页。例如：

- 后端请求 GitHub API 拉取 PR，页面显示“正在拉取 PR 元数据和 Diff”。
- Diff Parser 解析出 3 个修改文件，页面显示“已解析 3 个文件、42 行新增、18 行删除”。
- Context Builder 读取 `paginator.py`，页面显示“读取相关代码片段”。
- 符号检索查找 `OptimizedCursorPaginator` 的定义和引用，页面显示“跨文件搜索符号，找到 2 处引用”。
- 测试检索查找相关测试，页面显示“搜索分页器相关测试，未找到覆盖负索引的用例”。
- Verifier 请求专家补充证据，页面显示“Verifier 请求 Intent Agent 核验调用签名”。

这些动作必须真实发生后才展示。前端不把“模型正在思考”包装成工具调用，也不展示隐藏推理。

### 3.3 页面切换造成任务“像被中断”

- ReviewPage 卸载时关闭 EventSource。
- 后端任务仍继续运行，但其他页面没有全局任务状态。
- ResultPage 没有返回实时过程的入口。
- 用户无法区分“关闭了浏览器订阅”和“停止了服务端审查”。

### 3.4 五仓覆盖不可用

- 五个仓库由前端静态写死。
- `BenchmarkSummary` 只有总体指标，没有逐仓结果。
- 卡片不能进入仓库、案例或对应运行。
- 当前 Sentry 真实运行发现了 4 个非目标问题，但没有命中目标漏洞，页面无法表达这种差异。

### 3.5 当前真实运行暴露的运行时问题

`run-20260730-012450-d90a1b5b` 使用 1.1.6 默认并发 4，却启动了 6 个专家实例，导致排队；Verifier 先达到预算，团队阶段最终在约 320 秒超时。该运行状态为 `partial`，发现 4 个问题、拒绝 2 个候选，但没有命中“导入不存在的 OptimizedCursorPaginator”这一目标漏洞。前端必须准确展示“部分完成”“目标未命中”和超时原因。

该问题不能仅归因于仓库规模。直接原因包括：并发槽位少于专家实例数、Verifier watcher 生命周期只有 120 秒、团队阶段固定为 300 秒。1.1.7 已通过真实运行验证“并发 8 + Verifier watcher 覆盖完整团队生命周期”能够避免专家排队和晚到候选，1.1.6.1 应吸收这两项运行时修复。

## 4. 信息架构

### 4.1 全局任务层

在应用根组件增加 `ActiveRunBar`：

- 展示仓库、运行 ID、当前阶段、运行状态、耗时和候选数量。
- 审查运行时在所有页面常驻。
- 点击后返回 `/review/{run_id}`。
- 提供明确文案：“服务端任务继续运行，切换页面不会停止审查”。
- 终态后保留短摘要，并提供“查看过程”和“查看报告”两个入口。

SSE 订阅和当前运行状态提升到应用级运行控制器，不再由 ReviewPage 生命周期独占。页面只消费状态，不负责维持任务生命。

### 4.2 实时 Agent 作战室

作战室分为四层：

1. **输入与计划**：PR 元数据、Diff 文件、TeamLead 风险标签、分片计划和预算。
2. **并行专家拓扑**：按真实 Agent ID 展示实例，例如 `defect:ctx-1`、`intent:ctx-2`，每个实例显示负责文件、状态、工具活动、候选数量和耗时。
3. **Evidence Blackboard 与 Mailbox**：展示脱敏后的消息类型、发送者、接收者、关联候选和时间，不展示隐藏推理。
4. **验证流水线**：候选进入 Verifier 后，展示待验证、请求补证、已接受、已拒绝以及裁决摘要。

### 4.3 完整事件时间线

- 默认展示全部事件，按阶段分组。
- 支持按 Agent、事件类型和状态过滤。
- 支持自动跟随最新事件，也允许用户暂停滚动查看历史。
- 每条事件显示时间、主体、动作和安全摘要。
- 终态、失败、超时和降级事件使用明确视觉标识。

### 4.4 报告页

- 增加“返回审查过程”按钮。
- 运行中进入报告页时，显示实时摘要和返回入口，不让用户陷入不可返回的等待页。
- 终态报告显示 `completed`、`partial`、`failed` 的真实含义。
- `partial` 必须突出未完成阶段、已保存结果和人工复核提示。

### 4.5 五仓 Benchmark 评测矩阵

矩阵包含：

- 仓库和语言。
- 数据集案例总数、已核验数、已运行数。
- 真实目标命中数、其他 Finding 数、误报或拒绝数。
- 最近一次耗时和运行状态。
- 数据状态：`待补齐`、`待评测`、`运行中`、`已完成`、`部分完成`、`失败`。
- “查看案例”“查看运行”“回放过程”入口。

未运行仓库不显示 `0%`，而显示“待评测”，避免把缺失数据误解为零命中率。Fake 结果只能出现在单独的“离线链路验证”区域，并明确排除在真实命中率之外。

Sentry 当前真实记录应展示为：部分完成、目标漏洞未命中、其他 Finding 4 个、Verifier 拒绝 2 个、耗时约 319.87 秒，并关联 `run-20260730-012450-d90a1b5b`。

## 5. 工具活动如何展示

### 5.1 用户在页面上看到什么

工具区不展示抽象的内部函数列表，而展示一条可读的“审查操作流水线”：

| 页面文案 | 执行者 | 实际动作 | 可展示结果 |
|---|---|---|---|
| 拉取 GitHub PR | 输入加载器 | 请求 PR 元数据和 Diff | 仓库、标题、修改文件数、耗时 |
| 解析代码差异 | Diff Parser | 解析 unified diff | 文件数、增删行数、语言 |
| 读取相关代码 | Context Builder | 读取修改行附近代码 | 文件、行范围、字符数 |
| 搜索符号定义 | Context Builder | 搜索定义和跨文件引用 | 搜索词、命中文件数、证据数 |
| 查找相关测试 | Context Builder / Agent | 搜索测试文件和调用点 | 找到或未找到、文件数 |
| 执行静态扫描 | Semgrep Adapter | 运行只读规则扫描 | 规则数、信号数、降级状态 |
| 发布候选问题 | 专家 Agent | 写入 Mailbox 候选消息 | 文件、严重程度、证据数 |
| 请求补充证据 | Verifier | 定向请求专家核验 | 目标 Agent、候选 ID、核验主题 |
| 返回补证结果 | 专家 Agent | 回传证据或不确定结论 | 新证据数、结论摘要 |
| 生成审查报告 | Reporter | 持久化 JSON 和 Markdown | Finding 数、报告状态、耗时 |

每个工具活动卡片至少显示：执行者、动作、目标、状态、耗时和结果摘要。例如：

```text
上下文构建器 · 搜索符号定义                         184ms
目标：OptimizedCursorPaginator
结果：检查 3 个文件，发现 2 处引用，未确认 base 提交中存在定义
```

### 5.2 当前代码中已经存在什么

当前仓库已经实现以下只读能力：

- `safe_read`：读取仓库内指定文件和行范围。
- `search_code`：在仓库文本文件中搜索代码字符串。
- `find_related_tests`：根据修改文件名查找相关测试。
- `search_project_docs`：读取 README、架构、安全和贡献规范文档。
- `git_history`：查询文件最近提交历史。
- `git_blame`：查询指定代码行来源。
- `git_show`：读取指定提交摘要和差异。
- `run_semgrep`：可选执行 Semgrep，缺失时降级为空结果。
- `load_pr`：通过 GitHub API 或本地 Git 加载 PR/base-head 差异。
- `parse_diff`：把 unified diff 转换为修改文件和 hunk。
- Context Builder：组合文件读取、测试检索、文档检索、符号引用检索和 Semgrep 信号。

但这些能力目前分成了三种状态：

1. **已经实现且被 Context Builder 直接调用**：文件读取、代码搜索、测试检索、项目文档和 Semgrep。它们确实执行了，但绕过统一 Tool Registry，因此没有工具事件。
2. **已经实现但生产 Agent 很少或没有调用**：Git history、Git blame、Git show。测试证明接口可用，但真实审查通常看不到调用记录。
3. **存在工具注册框架但未完整接入生产链路**：`ToolRegistry` 能处理角色权限和输出裁剪，`AgentRuntime` 也能记录模型原生工具调用；当前生产专家主要消费预构建 ContextPack，没有把上述工具统一注册并暴露给 Agent。

因此本版本不是“凭空增加工具数量”，而是把真实存在的动作接入统一执行和事件层；随后再选择性地让 Agent 主动调用安全、只读、有预算的工具。

### 5.3 内部分层

**系统工具**由编排层调用：

- `github.load_pr`：读取 PR 元数据和 Diff。
- `git.load_diff`：读取本地 base/head 差异。
- `diff.parse`：解析修改文件和行范围。
- `context.read_file`：读取相关文件片段。
- `context.search_symbol`：跨文件符号引用检索。
- `context.find_tests`：定位相关测试。
- `static.semgrep`：执行可选静态扫描。
- `report.persist`：生成并保存报告。

**Agent 工具**由具体 Agent 在审查或补证阶段主动调用：

- `code.search`、`code.read`、`git.blame`、`tests.search`、`evidence.lookup` 等。

“发布候选”“请求补证”等 Mailbox 动作不是代码检索工具，但属于 Agent 协作动作，应在协作流水线中展示，不能混入工具调用计数。

### 5.4 公开事件

新增统一的公开工具事件字段：

```json
{
  "actor": "context_builder",
  "actor_type": "system",
  "tool_name": "context.search_symbol",
  "status": "completed",
  "target": "OptimizedCursorPaginator",
  "summary": "检索 3 个文件，获得 2 条相关证据",
  "duration_ms": 184
}
```

安全约束：

- 不公开完整文件内容、Token、Prompt 或模型原始响应。
- `target` 和 `summary` 必须经过长度限制与脱敏。
- 没有真实发生的调用不能生成事件。
- 专家只消费预构建上下文时，展示“读取上下文包”，不冒充主动搜索。

### 5.5 前端计数与文案

- 页面顶部显示“审查操作”总数，包含真实发生的系统工具和 Agent 工具。
- 每个 Agent 卡片只统计该实例主动调用或明确消费的工具，不把 PR 拉取算到专家名下。
- Mailbox 消息单独显示为“协作消息”，不计入工具数量。
- 如果专家只读取预构建 ContextPack，显示“已读取上下文包”，而不是“0 个工具”这种容易误解的裸数字。
- 如果某种能力没有执行，显示“未执行”及原因，例如“Semgrep 未安装，静态扫描已降级”，不能静默显示为零。

## 6. 自适应时间预算与 10 分钟硬上限

### 6.1 单一硬上限

单个 PR 从输入加载到报告持久化的全流程硬上限为 600 秒。600 秒既是比赛 SLA，也是不可突破的运行上限；到时立即停止剩余工作，保存 Agent 快照、已确认 Finding、已拒绝候选和超时原因，返回 `partial`，不在后台继续占用模型和资源。

### 6.2 按变更规模分配阶段预算

TeamLead 根据以下信号计算团队阶段软预算：

- 修改文件数。
- Diff 新增和删除行数。
- ContextPack 数量。
- 需要启动的专家实例数。
- 是否包含跨语言、依赖、配置和测试变更。
- 是否启用 Semgrep、跨文件符号检索或远程 GitHub 内容读取。

建议初始策略：

| 变更规模 | 示例 | 团队软预算 | 全局硬上限 |
|---|---|---:|---:|
| 小型 | 1–3 文件、少量上下文 | 240 秒 | 600 秒 |
| 中型 | 4–10 文件、多专家并行 | 420 秒 | 600 秒 |
| 大型 | 10 个以上文件或重检索 | 600 秒 | 600 秒 |

超过软预算时先请求 Agent 快照，停止低价值扩展检索，并给已经接近完成的 Verifier 留出受控收敛时间。所有阶段共享同一个 600 秒绝对截止时间，任何阶段不得通过独立超时叠加突破全局上限。

### 6.3 并发和 Verifier 生命周期

- 默认并发从 4 提升到 8，保证常见的“三个 ContextPack × 两类专家 + Verifier”无需排队。
- 并发仍可通过环境变量配置，最大值保持受控，避免模型接口被瞬时打满。
- Verifier watcher 生命周期覆盖完整团队阶段，而单次模型调用仍受独立 LLM timeout 限制。
- 专家完成初审后立即发布完成屏障；Verifier 收敛后广播终态，已注册专家及时退出。

### 6.4 前端展示

顶部任务条同时显示：

- 当前耗时。
- 根据规模计算的软预算。
- 600 秒全局硬上限。

接近截止时间时显示“正在收敛并保存当前结果”；达到 600 秒后显示“已到达 10 分钟上限，当前可用结果已保存”。

## 7. 状态管理与数据流

```text
POST /api/reviews
        ↓
全局 Run Controller 保存 activeRunId
        ↓
应用级 SSE 单例订阅
        ↓
Pinia 按 run_id 保存事件和派生状态
        ├─ ActiveRunBar
        ├─ ReviewPage 作战室
        ├─ ResultPage 实时/终态报告
        └─ HistoryPage / Benchmark Matrix
```

要求：

- 一个运行只建立一个实时 SSE 订阅。
- 路由切换不关闭活动运行订阅。
- 刷新页面后根据 URL 或持久化的 `activeRunId` 重新连接，并从服务端事件日志补齐。
- 使用 `sequence` 幂等去重。
- 收到终态后关闭 SSE，但保留完整事件用于查看和回放。
- 不把浏览器断线解释为服务端任务停止。

### 7.1 Replay 倍速控制

- 回放页提供 0.5×、1×、2×、4× 和 8× 倍速。
- 播放过程中可以切换倍速，无需重新开始。
- 提供暂停、继续、重新开始和拖到下一关键事件。
- “跳过空闲时间”开启后，把长时间无事件间隔压缩到最多 1 秒，但保持事件先后顺序。
- 页面显示“回放时间”和“原始运行时间”，避免把加速回放误解为真实审查耗时。
- 服务端 Replay 和本地离线 Demo 使用相同的倍速语义。

## 8. 后端公开契约调整

为支持真实过程展示，后端需要增加或扩展以下公开数据：

1. `review.started` 补充仓库和 PR 标题；加载成功后可以发送独立的 `review.metadata`，避免启动时尚未取得元数据。
2. 增加 TeamLead 计划事件，包含风险标签、上下文 ID、Agent 分片和预算摘要。
3. `agent.started` 补充 `context_id` 和负责文件。
4. 增加系统与 Agent 工具活动事件。
5. 增加公开 Mailbox 摘要事件，覆盖候选发布、补证请求、补证响应和终态广播。
6. Benchmark API 增加逐仓与逐案例结果，不要求前端自行扫描本地文件拼装。

所有新事件继续遵守公开字段白名单，不保存或暴露隐藏思维链。

## 9. 异常与降级处理

- SSE 断开：全局任务条显示“重新连接”，自动补齐事件；不显示“任务停止”。
- 后端不可用：保留最近状态并提供重试，不清空运行记录。
- Agent 超时：实例卡片显示超时和最后快照；整体运行显示 `partial`。
- 600 秒硬超时：停止剩余 Agent，持久化快照、当前 Finding 和明确警告，返回 `partial`。
- 工具失败：展示工具名、失败状态和中文安全摘要，不展示外部异常原文。
- Benchmark 缺失：显示“待补齐”或“待评测”，不显示零分。
- Fake 数据：只能标注为离线演示或离线链路验证。

## 10. 测试策略

### 10.1 前端测试

- 路由切换后应用级 SSE 不被关闭。
- 同一运行不会创建重复订阅。
- 刷新或重新进入作战室能够补齐历史事件。
- ActiveRunBar 在运行、重连、部分完成、失败和完成状态下显示正确。
- 多个 Agent 实例不会被折叠丢失。
- 工具分类和计数准确，零工具时有明确说明。
- 报告页可以返回过程页。
- 五仓未运行项显示“待评测”，不显示虚假 `0%`。
- Sentry 部分完成且目标未命中的数据展示正确。
- 接近 600 秒时显示收敛提示，到达上限后显示任务已停止且结果已保存。

### 10.2 后端测试

- 新增公开事件只包含白名单字段。
- 工具事件只在真实动作发生时发布。
- TeamLead 分片和 Agent 负责文件能通过 SSE 与 Replay 一致恢复。
- Benchmark 逐仓结果由案例报告确定性聚合。
- 缺失、Fake 和真实结果不会混算。
- 小、中、大三类 Diff 获得不同软预算，但全流程硬上限始终为 600 秒。
- 默认并发 8 时六个专家实例无需排队。
- Verifier watcher 覆盖团队生命周期，单次模型调用仍使用独立超时。

### 10.3 全链路验收

1. 发起真实 GitHub PR 审查。
2. 在作战室观察 PR 加载、Diff 解析、计划、六个专家实例、候选和裁决。
3. 审查过程中切换到历史页，确认顶部任务条继续更新。
4. 点击任务条返回作战室，确认事件序号连续且没有重复。
5. 进入报告页再返回过程页，确认后端任务未中断。
6. 打开五仓矩阵，确认已运行与待评测状态明确区分。
7. 使用 Replay 验证相同事件能恢复相同界面状态。
8. 在 Replay 页面切换 0.5×、1×、2×、4× 和 8×，确认事件顺序一致且切换倍速不会重复事件。

## 11. 实施边界与优先级

### P0：必须完成

- 应用级 SSE 与顶部全局任务条。
- 报告页返回作战室。
- 真实 Agent 实例展示。
- 完整可过滤时间线。
- 系统工具活动事件和诚实计数。
- 五仓评测矩阵及真实空态。
- 自适应软预算与 600 秒全流程硬上限。
- 吸收 1.1.7 的默认并发 8 与 Verifier 生命周期修复。

### P1：比赛亮点

- TeamLead 分片计划可视化。
- Mailbox 消息流和候选裁决关联。
- 工具耗时、目标和证据摘要。
- 单仓案例详情和运行回放入口。

### P2：时间允许再做

- 拓扑动画和消息飞线。
- 事件搜索、导出和高级筛选。
- 多个同时运行任务的任务中心。

本版本不修改模型 Prompt，不承诺修复 Sentry 目标漏洞命中能力；相关 Retrieval 优化应在独立实验分支完成。1.1.6.1 只负责真实、稳定、可理解地展示现有 Agent Team 运行，并补齐必要的公开事件契约。

## 12. 完成标准

满足以下条件后，1.1.6.1 才能登记为可用版本：

- 页面切换不会丢失活动运行的实时观察能力。
- 用户能从任意页面返回当前作战室。
- 能看到真实 Agent 实例、负责文件、工具活动、候选和 Verifier 裁决。
- 工具数量不再因为系统预处理未计入而长期显示为零，同时不制造虚假调用。
- 页面能用自然语言说明每项工具动作做了什么、得到什么结果，而不只显示内部工具名。
- 五仓卡片有明确的数据状态和可操作入口。
- 真实与 Fake Benchmark 严格分离。
- 后端、前端测试及生产构建通过。
- 至少使用一个真实运行和一个离线 Replay 完成全链路验收。
- 全流程在 600 秒内完成或以 `partial` 保存当前结果，不允许后台继续突破比赛时限。
