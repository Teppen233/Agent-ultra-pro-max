# ReviewCrew 三分钟演示脚本

## 录制口径

目标成片严格为 180 秒。原设计要求的七段内容时长分别为 20、20、50、35、35、30、20 秒，合计 210 秒；本脚本通过两段画中画重叠压缩 30 秒：

- 并行审查最后 15 秒叠加 Verifier 画面；
- Finding 最后 15 秒叠加 Benchmark 摘要。

每段内容仍获得规定展示时长，整片时间轴为 0:00–3:00。

演示优先使用前端内置离线 Replay，保证没有模型密钥或网络波动时仍能完整展示。离线事件是固定 Demo，不冒充真实 PR 结果；Benchmark 只展示 Fake quick，并明确不计入真实命中率。

## 录制前准备

在仓库根目录执行：

```powershell
python -m benchmark.runner --mode quick --runner fake
```

启动后端：

```powershell
python -m uvicorn reviewcrew.server.app:app --host 127.0.0.1 --port 8000
```

另开 PowerShell 启动前端：

```powershell
Set-Location .\frontend
pnpm dev
```

浏览器打开 `http://127.0.0.1:5173`。录制前确认：

- 首页“播放最佳离线回放”按钮可用；
- `benchmark/results/fake-quick/summary.json` 已生成；
- 浏览器缩放 100%，窗口至少 1440×900；
- 关闭通知、密钥窗口、终端历史和其他敏感内容；
- 不输入虚假的 GitHub PR，也不展示任何 API Key。

## 180 秒时间轴

| 时间 | 内容 | 独立时长 | 画面 |
|---|---|---:|---|
| 0:00–0:20 | 痛点 | 20s | 首页英雄区与“证据优先”说明 |
| 0:20–0:40 | 启动 PR | 20s | PR 输入框与离线回放入口 |
| 0:40–1:30 | 并行审查 | 50s | Agent Team 拓扑、阶段进度、事件时间线 |
| 1:15–1:50 | Verifier | 35s | 1:15 起以画中画叠加 Verifier，1:30 后切全屏 |
| 1:50–2:25 | Finding | 35s | Finding 证据卡与拒绝项 |
| 2:10–2:40 | Benchmark | 30s | 2:10 起叠加 Fake 摘要，2:25 后切全屏 |
| 2:40–3:00 | 优势总结 | 20s | 首页四项能力与总结字幕 |

## 分镜与口播

### 0:00–0:20 痛点：传统 AI Review 缺少可验证证据

画面：停留首页英雄区，轻微向下滚动到四项能力。

口播：

> 代码审查真正困难的，不是生成更多评论，而是确认问题确实由这次改动引入、能够触发，并且影响真实。ReviewCrew 把审查拆成“发现候选”和“独立验证”两步，只发布带修改行定位、触发条件、实际影响和代码证据的问题。

屏幕字幕：`高召回发现 → 独立反证 → 证据化发布`

### 0:20–0:40 启动 PR：真实入口与稳定演示分开

画面：依次指向 GitHub PR、本地仓库两个入口，不提交示例 URL；随后点击“播放最佳离线回放”。

口播：

> 系统支持 GitHub PR URL，也支持本地仓库的 base 和 head。真实审查使用配置好的 OpenAI 兼容模型；今天为了三分钟演示稳定性，我播放同一事件协议的离线 Replay。它不依赖模型和网络，也不会被写成真实评测成绩。

操作：点击“播放最佳离线回放”，进入运行页。

### 0:40–1:30 并行审查：流式 Agent Team

画面：展示阶段进度、600 秒预算、Agent Team 图和滚动事件。0:40–1:15 以全屏展示并行专家；1:15 开始在右下角叠加 Verifier 卡片，为下一段提前铺垫。

口播：

> Team Lead 先根据 diff、变更规模和风险分配预算。DefectAgent 聚焦静态缺陷、安全、并发和资源问题；IntentAgent 聚焦业务逻辑、状态机、契约和架构边界。两位专家并行，不是串行排队。候选一产生，就通过类型化 Mailbox 写入 Evidence Blackboard，并立即进入验证。普通代码负责上下文、预算、去重、事件和报告，模型只做需要判断的工作。整个 PR 受十分钟，也就是六百秒的全局 watchdog 约束。

屏幕字幕：`DefectAgent ∥ IntentAgent`、`Mailbox`、`Evidence Blackboard`、`600s watchdog`

### 1:15–1:50 Verifier：在专家完成前开始反证

画面：1:15–1:30 保持 Agent Team 主画面，同时放大 Verifier 状态；1:30–1:50 切到 Verifier 接受/拒绝事件和时间线。

口播：

> Verifier 是持续监听的 watcher，不等待两位专家全部结束。它检查问题是否在修改行、是否可达、是否有上游保护、是否属于当前 PR，并校准严重度。证据不足时，它最多向原专家发起一次定向补证。这里一个候选证据成立被接受，另一个无法证明实际影响被拒绝；拒绝项不会进入最终 Finding。

屏幕字幕：`先反证，再发布`、`每个 Finding 最多一次补证`

### 1:50–2:25 Finding：展示证据而非隐藏推理

画面：打开最终 Finding 卡片，依次指向严重度、文件行号、触发条件、影响、证据和建议。2:10 开始在角落叠加 Benchmark 摘要。

口播：

> 最终结果不是一句泛化风险提示。每条 Finding 都有文件和修改行定位、触发条件、真实影响、证据片段和修复建议。报告只保存可审计摘要，不保存完整 Prompt、模型原始响应或隐藏思维链。运行同时生成 JSON、中文 Markdown 和事件 JSONL，既能给机器消费，也能供人复核和回放。

屏幕字幕：`定位 + 触发 + 影响 + 证据 + 建议`

### 2:10–2:40 Benchmark：只展示真实已有的 Fake 结果

画面：2:10–2:25 保留 Finding 主画面并叠加摘要；2:25–2:40 全屏展示 Fake quick 数据：5 完成、2 命中、3 非目标、接受/拒绝 5/1、真实命中率为空。

口播：

> 评测链路提供 quick、case 和 full 三种模式。当前公开可复现的是五语言离线 Fake：五个案例全部完成，观察到两个三层命中，三个非目标 Finding，Verifier 接受五个、拒绝一个。这个百分之四十只验证 Runner、Judge 和报告，不计入真实命中率。五个公开 Greptile PR 仍待人工回溯上游修复和目标位置，我们不会伪造真实成绩。

屏幕字幕：`Fake / Offline`、`real_catch_rate = null`、`不计入真实命中率`

### 2:40–3:00 优势总结

画面：回到首页能力条，依次高亮 Diff 中心、流式协作、证据优先、稳定回放。

口播：

> ReviewCrew 的优势是四点：围绕 diff 按需取上下文；两位专家和 Verifier 流式协作；用 Evidence Blackboard、版本化 Skills、Hooks 和传统工具形成可审计证据链；最后用六百秒预算、中文报告和 Replay 保证可控交付。真实模型结构化连通已经验证，真实 PR 命中仍以之后的可回放结果为准。

结束字幕：`ReviewCrew — 让每一行改动都经得起独立验证`

## 现场故障降级

- 后端或模型不可用：立即点击首页离线 Replay，不等待现场重试。
- GitHub 网络不可用：不打开公开 PR 页面，展示评测报告中已保存的链接与“未运行”状态。
- Benchmark 命令失败：使用录制前已生成的 `summary.json`，并说明生成时间；不得手工修改数字。
- 页面刷新丢失当前状态：从历史页选择已有 run；若没有事件文件，回到内置 Demo。
- 时间超出：优先删去页面滚动停顿，不删“Fake 不计入真实命中率”和“尚无真实 PR 结果”两句口径。
