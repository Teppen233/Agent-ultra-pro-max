# ReviewCrew 演示脚本（3 分钟）

> 使用 Fake 模式演示全流程，无需 API Key。所有命令在 PowerShell 下执行。

---

## 分镜 1：痛点（20 秒）

**画面**：终端打开，展示一个 GitHub Pull Request 页面。

**动作/台词**：

"你刚提交了一个 PR，在 CI 通过后 @ 同事审查。

但他可能很忙，两天后回复：'LGTM'。

你可能想先自己检查一遍，但 500 行 diff，十几个文件——光看一遍就要半小时。"

**关键信息**：指出人工审查的两个痛点——延迟高（半天到两天）、质量不稳定（LGTM 文化）。

---

## 分镜 2：启动审查（20 秒）

**画面**：切换到 PowerShell 终端，展示项目目录。

**动作/台词**：

"ReviewCrew 的解决方案：输入一个 PR URL，两个 AI 专家并行审查，30 秒内给你一份结构化的缺陷报告。"

**操作**：

```powershell
# 展示项目结构
ls reviewcrew/

# 展示 .env 配置（Fake 模式无需真实 Key）
cat .env.example
```

**关键信息**：强调 Fake 模式可以离线运行，不需要 API Key。

---

## 分镜 3：并行审查（50 秒）

**画面**：运行 CLI 命令，终端显示审查进度。同时打开另一个窗口展示 Vue 3 前端。

**动作/台词**：

"让我们用 Fake 模式运行一次本地仓库审查。它做了六件事："

**操作**：

```powershell
# 启动审查（Fake 模式）
python -m reviewcrew.cli review --repo . --base develop-1.1 --head feature/x
```

**讲解六阶段流程**（每个阶段 5-8 秒）：

1. **PR 加载**："首先，从 GitHub API 或本地 Git 加载 PR 的 diff 数据。"
2. **上下文构建**："然后，围绕每个修改行收集上下文——封闭函数、同目录文件、相关测试。"
3. **并行审查**："DefectAgent 检查注入、空指针、资源泄漏；IntentAgent 对照 PR 描述检查意图对齐。"（重点：两个 Agent 并行工作）
4. **去重**："两个专家可能发现同一个问题——去重模块用纯逻辑合并重复发现。"
5. **验证**："VerifierAgent 做七项独立检查：PR 引入、修改行定位、触发路径可达..."
6. **报告**："最后输出 Markdown 报告，最多展示 8 条问题。"

**关键信息**：两个 Agent 并行工作才是性能优势的核心。

---

## 分镜 4：Verifier 验证（35 秒）

**画面**：切换到代码，展示 `verifier.py` 中的验证逻辑。

**动作/台词**：

"很多 AI 审查工具的问题是误报太多——模型可能说第 300 行有问题，但那行根本没被修改过。"

**展示 Verifier 七项检查**：

1. 是否由当前 PR 引入
2. 是否定位到修改行
3. 触发路径是否可达
4. 是否存在上游保护
5. 是否重复
6. 严重度和置信度是否合理
7. 证据是否充分

**台词**：

"Verifier 只通过这七项检查的 Finding。不通过的直接拒绝——不会出现在最终报告中。"

**关键信息**：Verifier 是 ReviewCrew 的质量保证，解决 AI 误报问题。

---

## 分镜 5：结果展示（35 秒）

**画面**：展示审查报告、事件流和前端界面。

**动作/台词**：

"审查完成后，你获得三样东西："

**操作**：

```powershell
# 查看运行记录
ls runs/

# 查看 JSON 结果
cat runs/<run_id>/result.json

# 查看 Markdown 报告
cat runs/<run_id>/report.md

# 启动前端实时查看（另一个终端）
uvicorn reviewcrew.server.app:app --reload
cd web && npm run dev
```

**台词**：

"第一，完整的 JSON 结果——可以接入 CI/CD。第二，中文 Markdown 报告——直接回复在 PR 评论区。第三，SSE 事件流——前端实时显示审查进度，不再是一个黑盒。"

**关键信息**：三种输出格式覆盖自动化和人工两种使用场景。

---

## 分镜 6：Benchmark 评测（30 秒）

**画面**：展示 `benchmark/dataset.yaml` 和评测运行。

**动作/台词**：

"我们怎么知道 ReviewCrew 真的有用？我们用 Greptile Benchmark——5 个来自 Sentry、Cal.com、Grafana、Keycloak、Discourse 的真实历史 Bug。"

**操作**：

```powershell
# 展示评测数据集
cat benchmark/dataset.yaml

# 运行评测
python -m benchmark.runner --mode quick --runner fake
```

**台词**：

"每个案例都有已知漏洞的文件和行号。三层判定——文件命中、行号命中、语义命中——全部通过才算成功。"

**关键信息**：Benchmark 是客观的质量度量，不是自说自话。

---

## 总结（20 秒）

**画面**：回到终端，总结三个核心卖点。

**台词**：

"ReviewCrew 做三件事，人和传统工具都不擅长：

1. **并行专家审查**——30 秒完成两个人一天的审查范围
2. **独立验证过滤**——VerifierAgent 大幅降低误报
3. **Benchmark 可度量**——不是感觉有用，而是数据证明有用

项目地址：[repo-url]
支持 GitHub PR 和本地仓库，开箱即用。"

**关键信息**：结尾留下清晰的行动号召。
